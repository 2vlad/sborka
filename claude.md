# claude.md — карта репозитория и правила работы агента (map, not manual)

Этот репозиторий развивается в agent‑first режиме: **люди задают намерение и проверяют результат, агенты исполняют**.
Цель — максимальная скорость без распада качества за счёт **структуры, инвариантов и обратных связей**, а не за счёт ручного кодинга.

> Важно: этот файл — **карта**, а не энциклопедия. Не раздувайте его.  
> Любое “знание, которое должно жить долго” фиксируйте в `docs/` и добавляйте ссылку в `docs/index.md`.

---

## 1) С чего начинать любую задачу (progressive disclosure)

1. Откройте `docs/index.md` — это **точка входа и оглавление** системы знаний.
2. Найдите источники истины по теме (обычно):
   - `docs/product/` — продуктовые требования (PRD, Product Requirements Document — документ требований), UX‑флоу, контент‑модель.
   - `docs/architecture/` — архитектура, границы доменов, допустимые зависимости.
   - `docs/quality/` — качество, надёжность, тест‑стратегия, “quality score”.
   - `docs/exec-plans/active/` — активные планы исполнения и decision log (журнал решений).
3. Если нужного документа **нет** — **создайте маленький документ** в `docs/`, внесите в `docs/index.md`.
   - Не храните критичное знание в чатах/таск‑трекере: “не в репо — значит не существует”.

---

## 2) Система знаний: `docs/` — system of record

**Правило:** всё, что влияет на правильность продукта/архитектуры/качества, должно быть:
- **в репозитории**,
- **версионировано**,
- **находимо** через `docs/index.md`,
- **проверяемо механически** (линтеры/тесты/CI).

### Минимальная структура `docs/` (целевая)
- `docs/index.md` — оглавление (таблица содержания) по всем документам.
- `docs/product/` — PRD, UX, контент‑модель, API‑контракты, события стриминга.
- `docs/architecture/` — карта доменов, слои, разрешённые зависимости, контракты.
- `docs/quality/` — качество, надёжность, безопасность, “quality score”.
- `docs/exec-plans/active/` и `docs/exec-plans/completed/` — планы исполнения.
- `docs/references/` — референсы: гайды, примеры уроков, форматы.
- `docs/generated/` — автогенерируемые артефакты (схемы, спецификации), не редактировать вручную.

### Требование к документам (для док‑линтера)
Каждый документ в `docs/` должен содержать вверху минимальные метаданные:
- `Status:` draft | active | validated | deprecated
- `Owner:` (роль/команда, не обязательно человек)
- `Last reviewed:` YYYY‑MM‑DD
- `Links:` как минимум 1–2 ссылки на соседние документы (чтобы граф знаний был связным)

## 3) Протокол работы (PR‑loop)

Работа всегда оформляется через PR (Pull Request — запрос на внесение изменений) / MR (Merge Request — запрос на слияние).

### Для каждой задачи
1. **Сформулируйте намерение**: что меняется и почему (1–3 абзаца).
2. **Зафиксируйте acceptance criteria** (критерии приёмки): проверяемые, без двусмысленности.
3. **Сделайте план исполнения**:
   - маленькие изменения: короткий план в описании PR;
   - средние/крупные: `docs/exec-plans/active/YYYY-MM-DD-<slug>.md` с:
     - Goal / Non‑goals
     - Milestones
     - Test plan
     - Decision log (что решили и почему)
4. **Делайте depth‑first**: если что-то не получается — это сигнал, что не хватает возможности/инструмента/ограничения.
   - Исправление почти всегда: **сделать систему более “легибельной” и проверяемой**, а не “попросить сильнее”.
5. **Самопроверка до PR**: запуск тестов/линтеров/проверок, обновление docs, доказательство UI‑изменений.
6. **Маленькие PR > большие PR**: быстрее обратная связь, дешевле исправления.
7. Если в CI есть флейки (нестабильные тесты): **фиксить быстро отдельным PR**, не держать основной PR в заложниках бесконечно.

### Когда эскалировать человеку
Только когда нужен человеческий judgement:
- продуктовый компромисс,
- конфликт требований,
- изменение “золотого принципа”,
- неясный смысл задачи после чтения `docs/`.

## 4) “Золотые принципы” этого проекта (их надо кодировать в инварианты)

Эти правила должны **жить в коде и проверках**, а не только в тексте.

### 4.1. Контракты и границы
- Нельзя “угадывать” формы данных. Любые входы/выходы на границах (API, события, хранилище) должны быть **явно валидированы схемами**.
- Любой новый контракт: **тип + валидатор + тест**.

### 4.2. Детерминированная структура, вероятностное наполнение
- Структура учебного контента хранится как **дерево блоков** со стабильными `block_id`.
- Модели заполняют **внутрь блоков**, но не ломают структуру.

### 4.3. Стриминг — событийный
- UI не “читает поток текста”, UI подписан на **типизированные события** и обновляет состояние.
- События — часть публичного контракта: фиксируйте в `docs/product/streaming-events.md` и покрывайте тестами.

### 4.4. Изображения: “бронь места → подстановка”
- Если картинка уходит на генерацию, в документе заранее создаётся **placeholder‑блок** с фиксированным размером/отношением сторон.
- Когда ассет готов, он **подставляется в тот же блок**, без скачков верстки (no layout shift).

### 4.5. Промпты — это код
- Промпты/шаблоны/рубрики версионируются и тестируются.
- Любое изменение промптов должно сопровождаться:
  - фикстурой (пример входа),
  - ожидаемой структурой (snapshot),
  - регресс‑проверкой.

## 5) Механические проверки (enforce, don’t beg)

Этот репозиторий должен иметь (или вы должны добавить) проверяемые инварианты:

- форматирование (formatter)
- линт (lint)
- типизация (typecheck) — если применимо
- юнит‑ и интеграционные тесты
- структурные тесты архитектуры (dependency direction / layer rules)
- док‑линтер:
  - каждый doc в `docs/` индексирован в `docs/index.md`
  - есть метаданные (`Status/Owner/Last reviewed`)
  - ссылки не битые
- eval‑харнесс (evaluation harness — контур оценки) для LLM‑выходов:
  - “golden fixtures” (эталонные примеры)
  - snapshot‑тесты структуры/событий
- UI‑изменения:
  - скриншоты/видео‑артефакты или e2e (end‑to‑end — сквозные) тесты

> Если правило “важно всегда” — оно должно быть в линтере/тесте с **понятным сообщением**, которое подсказывает агенту, как исправить.

## 6) Легибельность приложения для агентов (feedback loops)

Стройте систему так, чтобы агент мог сам себя проверять:

- Приложение должно запускаться локально предсказуемо (одна команда), желательно изолируемо для параллельных задач.
- Логи должны быть **структурированными**, ключевые user journeys (пользовательские сценарии) — измеримыми.
- Для UI критично иметь воспроизводимый сценарий проверки (скрипт/тест), а не ручные шаги “потыкать”.

Если агент не может увидеть/измерить эффект изменения — это долг, который быстро убьёт скорость.

---

## 7) Док‑гарденинг и “сборка мусора” (entropy control)

Технический долг — это проценты. Его надо платить маленькими платежами.

- Введите регулярный “doc gardening”: агент сканирует `docs/` на:
  - устаревшие `Last reviewed`,
  - документы без ссылок/без индекса,
  - противоречия с кодом/контрактами,
  и открывает короткие PR на исправления.
- Введите регулярный “quality sweep”: обновление `docs/quality/QUALITY_SCORE.md` и PR на точечные улучшения.

---

## 8) Definition of Done (DoD — определение готовности)

Изменение считается готовым, когда:
- критерии приёмки выполнены и проверены,
- все проверки проходят локально и в CI (Continuous Integration — непрерывная интеграция),
- документация обновлена (или явно не требуется),
- новые инварианты закреплены механически (тест/линт), если они важны долгосрочно,
- UI‑изменения имеют доказательство (артефакты) и/или покрытие e2e,
- PR небольшой, понятный, обратимый.

## 9) Деплой (Railway)

- **Проект:** single‑service на Railway, URL: `https://sborka-production.up.railway.app`
- **Сборка:** `Dockerfile` (multi‑stage: Node собирает фронтенд → Python раздаёт бэкенд + статику)
- **Деплой:** `railway up` из корня или git push (если подключён repo в Railway dashboard)
- **Env‑переменные:** `OPENROUTER_API_KEY` (обязательна), остальное — дефолты
- **Проверка после деплоя:** открыть URL, убедиться что landing грузится и `/docs` отвечает
