# PRD: Генеративная образовательная платформа (веб‑прототип)

## 0) Краткое резюме

**Что делаем:** веб‑интерфейс (без перезагрузок страницы), где пользователь вводит образовательный запрос. Система:

1. определяет “размер” запроса: **урок / тема / модуль / профессия** (по вашей шкале длительности),
2. строит структуру до уровня уроков,
3. генерирует контент (Markdown + интерактивные элементы: квизы/практика/диалоги),
4. параллельно запускает генерацию иллюстраций: **в контенте заранее появляются плейсхолдеры** (“места под картинки”), а при готовности по API картинки **подставляются** в эти места,
5. показывает прогресс и результат **стримингом** (инкрементально) без перезагрузок.

**Фокус прототипа:** качество (можно больше вызовов в модели), наблюдаемость процесса (что происходит) и адекватная навигация по вложенности (как в вашем примере “Содержание → модуль/спринт → тема → урок/страница”).

---

## 1) Цели

### 1.1. Продуктовые цели

* Дать пользователю быстрый “первый артефакт” — понятную структуру и первые уроки по его запросу.
* Показать, что система умеет **масштабировать** запрос до правильного формата (урок/тема/модуль/профессия) и **раскладывать** до уроков.
* Дать ощущение “живого” производства контента: стриминг, статусы, плейсхолдеры иллюстраций, появление элементов по мере готовности.

### 1.2. Цели качества контента

* Уроки соответствуют вашим методическим принципам и структуре (12 блоков, практики, финальные квизы, нейтральный фидбек и т. д.). 
* Тон: спокойный наставник, без фальши и давления. 
* Структурность: контент не “простыня”, а документ с оглавлением, секциями, интерактивом.

### 1.3. Технические цели

* Вся работа — **в вебе**, без перезагрузок страницы (**SPA, Single Page Application — одностраничное приложение** или эквивалентная архитектура).
* Стриминг — событийный (не просто поток токенов), чтобы UI мог рисовать прогресс и частичные результаты.
* Иллюстрации: “бронь места” → асинхронная подстановка по готовности.

---

## 2) Не цели (вне скоупа прототипа)

* Платежи, подписки, биллинг.
* Полноценная авторизация/профили/социальные функции.
* Маркетплейс курсов, рейтинги, сертификаты.
* Полноценный редактор/верстальщик курсов как в CMS (Content Management System — система управления контентом).
* Мобильные приложения (достаточно responsive‑веб).
* Глубокая LMS‑логика (Learning Management System — система управления обучением): дедлайны, домашки с автопроверкой по множеству типов, групповое обучение и т. д.

---

## 3) Пользователи и роли

### 3.1. Ученик (основной пользователь прототипа)

* Вводит запрос (“хочу разобраться в модулях JS”, “хочу стать фронтенд‑разработчиком”, “как устроена архитектура React‑приложения”).
* Получает структуру и первые учебные материалы.
* Проходит квизы/практики прямо в интерфейсе.

### 3.2. Автор/методист прототипа (вы)

* Задаёт **tone of voice** и методические принципы (включая структуру урока, правила квизов/практики, типы контента). 
* Определяет набор поддерживаемых блоков: текст, код, иллюстрации, квизы, практика, задания на закрепление.
* Может перегенерировать отдельные уроки/блоки.

---

## 4) Основные определения и размеры

Система должна классифицировать запрос и выбрать формат:

* **Урок**: 10–30 минут.
* **Тема**: 2–3 урока.
* **Модуль**: 1–2 вечера.
* **Профессия**: 1–6 месяцев.

Внутренне всё — один граф/дерево контента, просто “корень” разный.

---

## 5) Пользовательские сценарии (User journeys)

### Journey A: “Сгенерировать обучение из запроса”

1. Пользователь открывает страницу генерации.
2. Вводит запрос.
3. Нажимает “Собрать программу”.
4. UI начинает стримить события:

   * система показала выбранный формат (урок/тема/модуль/профессия) и оценку масштаба,
   * показала структуру (оглавление) с уровнями вложенности,
   * начала генерацию первого урока.
5. Пользователь кликает по элементам структуры слева и читает контент справа.

**Критерий успеха:** за 1–2 минуты пользователь уже читает первый урок, видит оглавление и понимает масштаб.

---

### Journey B: “Профессия/длинный запрос — сначала скелет, потом по требованию”

1. Запрос классифицирован как “профессия”.
2. UI показывает:

   * программу (модули/темы/уроки — названия, цели, примерные длительности),
   * выделенный “первый модуль” (или первые 2–3 урока) к генерации.
3. Пользователь нажимает “Сгенерировать следующий урок/тему/модуль”.

**Критерий успеха:** не генерируем 6 месяцев контента за раз; выдаём управляемый “первый кусок”.

---

### Journey C: “Иллюстрации: бронь → подстановка”

1. Во время генерации урока система решает, что нужны иллюстрации.
2. UI показывает в тексте зарезервированные блоки (плейсхолдеры) с подписью и индикатором “генерируется”.
3. Как только изображение приходит по API, UI заменяет плейсхолдер на картинку без перезагрузки и без скачков верстки (layout shift).

**Критерий успеха:** место под изображение фиксировано заранее (по размеру/соотношению сторон), контент не прыгает.

---

### Journey D: “Перегенерация”

1. Пользователь/автор видит, что один урок вышел слабым.
2. Нажимает “Перегенерировать урок” или “Перегенерировать блок”.
3. UI создаёт новую версию и показывает дифф/переключение версии (минимально — просто “Версия 2”).

**Критерий успеха:** точечная итерация без пересборки всего курса.

---

## 6) Информационная архитектура (навигация и вложенность)

Ориентируемся на ваш пример:

* **Содержание (root)** — список верхнего уровня (модули/спринты/разделы) с количеством уроков.
* При клике — страница **модуля/спринта** с оглавлением тем/уроков.
* При клике — страница **темы/урока** с оглавлением внутренних секций.

### Требования к UI‑навигации

* Левый сайдбар: дерево структуры (сворачиваемые узлы).
* Хлебные крошки (breadcrumbs): “Профессия → Модуль → Тема → Урок”.
* Внутри урока — оглавление секций (автогенерация по заголовкам) как в примере.

## 7) Требования к контенту (методика и tone of voice)

Источник требований — ваш гайд. 

### 7.1. Tone of voice (обязательное)

* Спокойный наставник: честно, практично, без фальшивого восторга и “давления”.
* Обращение на “вы”, гендерно‑нейтрально.
* Без стоп‑фраз и риторических вопросов.

### 7.2. Структура урока (обязательная)

Урок строится блоками (порядок значим):

1. Введение (через проблему),
2. “Из этого урока вы узнаете”,
3. Теория 1 + концепт,
4. Практика 1 с самопроверкой,
5. Теория 2 + развитие,
6. Практика 2 с самопроверкой,
7. Завершение теории,
8. Финальная проверка знаний (квизы),
9. Текст успеха,
10. Ключевые мысли,
11. Полезные материалы,
12. “В следующей серии”. 

### 7.3. Квизы и практика

* Квизы проверяют понимание, дистракторы правдоподобные, фидбек нейтральный.
* Два практических задания минимум, с критериями самопроверки. 

### 7.4. Иллюстрации

* Иллюстрация идёт **после** объясняющего текста и дополняет его.
* Урок не начинается с иллюстрации. 

---

## 8) Формат контента (что генерируем и как рендерим)

Чтобы одновременно иметь:

* стабильную структуру,
* возможность стриминга,
* интерактивные блоки,
* плейсхолдеры под изображения,

нужен **канонический формат** + рендер в Markdown.

### 8.1. Канонический формат: “документ из блоков”

Система хранит урок как массив блоков (AST, Abstract Syntax Tree — абстрактное синтаксическое дерево), где каждый блок имеет:

* `id`
* `type`
* `status` (planned / generating / ready / error)
* полезную нагрузку (markdown / quiz schema / image asset id)

**Пример типов блоков (минимум для прототипа):**

* `heading` (h2/h3),
* `markdown` (текст, списки, код),
* `quiz_single` / `quiz_multi`,
* `practice_task`,
* `callout` (спец‑вставки в духе `{quiz-task}` из примера),
* `dialog` (как в примере урока),
* `image` (плейсхолдер + потом подстановка).

Пример урока с “Action / Dialog / Select” показывает, что такой блоковый подход органичен. 

### 8.2. Рендер

* В UI блоки рендерятся в привычный Markdown‑документ, но интерактивные блоки — отдельными компонентами.
* Оглавление строится по `heading`.

## 9) Генеративный пайплайн (качество > стоимость)

### 9.1. Пайплайн верхнего уровня

1. **Classifier + Planner**: определить масштаб (урок/тема/модуль/профессия), выдать структуру.
2. **Scaffold**: для выбранного “первого урока” построить каркас: заголовки, блоки урока, места под иллюстрации (плейсхолдеры).
3. **Fill blocks**: заполнить блоки содержанием (стримингом).
4. **Critic → Revise**: проверка на соответствие гайду и правка (можно на уровне блока или целого урока).
5. **Assets**: иллюстрации параллельно: prompt → генерация → подстановка.

### 9.2. Почему нужен Scaffold (каркас) до текста

Это ключ к “броне” мест под картинки и к стабильной структуре урока:

* каркас создаёт `image`‑блоки с фиксированными параметрами (например, ratio 16:9),
* UI сразу рисует плейсхолдер,
* генерация изображений стартует, пока текст ещё дописывается.

## 10) Требования к интерфейсу (Web, без перезагрузок)

### 10.1. Главный экран: ввод запроса

* Textarea для запроса.
* (Опционально) “уровень” (новичок/средний/продвинутый), “цель” (понять/уметь сделать) — если не указано, считаем `unknown`.
* Кнопка “Собрать программу”.
* История последних 5–10 сессий (можно локально в браузере).

### 10.2. Экран результата: двухпанельный режим

**Слева:** дерево структуры (“Содержание”), уровни вложенности, статусы генерации.
**Справа:** документ урока (Markdown + интерактив).

Верхняя панель:

* текущий статус (“Планируем”, “Генерируем урок 1”, “Генерируем иллюстрации 2/3”),
* прогресс‑индикатор,
* кнопки: “Следующий урок”, “Перегенерировать урок”, “Скачать в Markdown”.

### 10.3. Стриминг в UI

Требование: пользователь видит прогресс *семантически*, а не только “текст печатается”.

Поэтому UI должен уметь:

* добавлять новые блоки по событиям,
* менять статус блока,
* подставлять результат в конкретный блок.

### 10.4. Плейсхолдеры изображений (“бронь места”)

**Требования:**

* Плейсхолдер имеет фиксированный размер (через заданное `aspectRatio` и minHeight).
* Плейсхолдер показывает:

  * подпись/alt‑текст,
  * статус (queued/generating),
  * кнопку “перегенерировать” (опционально).
* Когда изображение готово:

  * UI подменяет содержимое плейсхолдера на `<img>` без изменения размеров контейнера (чтобы не было прыжка).

### 10.5. Интерактивные элементы (минимум)

* Single choice quiz (выбор одного варианта) + нейтральный фидбек.
* Multi choice quiz (выбор нескольких).
* Практическая задача: описание + “Показать критерии самопроверки”.
* Диалоговый блок (как в примере). 

---

## 11) Событийная модель (стриминг без перезагрузок)

Рекомендуемый подход: **SSE (Server‑Sent Events — серверные события)** или WebSocket (если нужна двунаправленность). В PRD фиксируем требования, а конкретная реализация — на инженеринге.

### 11.1. Принцип

UI подписывается на поток событий конкретной “сессии генерации” и обновляет состояние по мере прихода событий.

### 11.2. Минимальный набор событий

* `session_created`
* `classification_ready` (scale, confidence, time estimate)
* `outline_ready` (дерево контента)
* `lesson_scaffold_ready` (создан набор блоков, включая image placeholders)
* `block_started` (block_id)
* `block_delta` (block_id, markdown_chunk) — если стримим кусками
* `block_ready` (block_id, payload)
* `asset_reserved` (asset_id, block_id, aspect_ratio, caption)
* `asset_generation_started` (asset_id)
* `asset_ready` (asset_id, url)
* `error` (scope: session/lesson/block/asset)
* `done`

## 12) API (Application Programming Interface — программный интерфейс) — верхнеуровнево

### 12.1. Сессии

* `POST /api/sessions`
  Вход: `user_request`, `config_id` (tone/method), параметры.
  Выход: `session_id`.

* `GET /api/sessions/{session_id}/events`
  Стрим событий (SSE/WebSocket).

### 12.2. Генерация

* `POST /api/sessions/{session_id}/generate`
  Запускает pipeline (plan → scaffold → fill → revise).

* `POST /api/sessions/{session_id}/lessons/{lesson_id}/regenerate`
  Перегенерация урока.

* `POST /api/sessions/{session_id}/blocks/{block_id}/regenerate`
  Перегенерация конкретного блока.

### 12.3. Ассеты (изображения)

* `POST /api/assets`
  Создание ассета (reserve) + старт генерации.

* `GET /api/assets/{asset_id}`
  Метаданные/статус/URL.

## 14) Нефункциональные требования

### 14.1. Производительность

* Time‑to‑first‑feedback: UI получает `classification_ready` быстро (в идеале < 2–3 секунд).
* UI не блокируется во время стриминга; скролл и навигация остаются отзывчивыми.

### 14.2. Надёжность

* Переподключение к стриму: при потере сети UI восстанавливает подписку и догружает состояние.
* Ошибки по блокам не “убивают” всю сессию: если упала картинка, урок всё равно читаем.

### 14.3. Качество контента (валидация)

* Автоматический чек перед “готово”: соответствие структуре урока и правилам гайда (хотя бы критиком‑LLM). 
* Явные статусы: “нужно внимание” (если критик нашёл нарушения).

### 14.4. Доступность (минимум)

* Клавиатурная навигация по оглавлению.
* ARIA‑лейблы для квизов и кнопок.
* Контраст и фокус‑стили (без ухода в дизайн‑систему).

### 14.5. Приватность

* В прототипе: предупреждение “не вводите персональные данные”.
* Логи: не сохранять сырой пользовательский текст без необходимости (или хранить только при включённом debug‑режиме).

## 15) Метрики успеха прототипа

**Продуктовые:**

* % сессий, где пользователь дошёл до открытия первого урока.
* Среднее время до первого “готового” урока.
* Количество кликов по структуре (навигация работает / контент вызывает интерес).
* Доля перегенераций (сигнал качества/контроля).

**Технические:**

* Среднее время генерации каркаса урока.
* Среднее время генерации одного блока.
* Среднее время генерации изображения и % ошибок по ассетам.
* Количество “layout shifts” при подстановке изображений (должно быть ~0).

**Контентные (эвристики):**

* Процент уроков, проходящих чек‑лист гайда без серьёзных замечаний.

## 16) Риски и как с ними жить

1. **Галлюцинации фактов/неверные утверждения.**
   Митигация: critic‑проход + явная политика “если не уверен — не утверждай”, и/или подключение источников в будущем.

2. **Разъезд структуры урока (LLM забывает блоки).**
   Митигация: scaffold‑этап (каркас жёстко задаёт блоки) + генерация “внутрь блоков”.

3. **Прыжки верстки из‑за поздних картинок.**
   Митигация: плейсхолдеры с фиксированным ratio, подмена контента внутри.

4. **Слишком дорогая генерация при многопроходности.**
   Митигация: по умолчанию “высокое качество” для прототипа, но архитектура должна позволять переключить режим.

---

## 17) MVP (минимально жизнеспособный прототип) — что точно должно быть

**MVP‑1 (вертикальный срез):**

* Ввод запроса.
* Классификация масштаба + структура.
* Генерация **первого урока** (каркас → наполнение).
* 1–2 иллюстрации с бронью места и подстановкой.
* 1 квиз single choice + 1 практика.
* Навигация по структуре в левой панели.
* Без перезагрузок; стриминг событий.

**MVP‑2 (усиление):**

* “Следующий урок” по структуре.
* Перегенерация урока.
* Multi choice quiz.
* История сессий.

## 18) Приложения и исходные ориентиры

* Гайд по tone of voice, структуре урока, квизам, практике и оформлению. 
* Пример урока с интерактивными вставками (Action/Dialog/Select/{quiz-task}).
